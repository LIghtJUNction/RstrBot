# RstrBot 工程质量与实现目标

日期：2026-10-28。本文定义实现者应交付的性质和证据，不提供源代码或预先承诺某个未经验证的依赖版本。

## 1. Rust 代码品味

主要参考：[BeautifulRust 的 rust-best-practices](https://github.com/morganlinton/BeautifulRust/blob/58757ee890da9b3c8d5b785adc7a8d53cce27307/skills/rust-best-practices/SKILL.md)。本项目选择以下可审查目标，不把整套指南机械当作业务需求：

- 类型表达真实差异：用户、工作区、会话、运行和插件身份不能随意混传；缺失值、状态和错误有明确表达。
- 模块默认私有，公共接口只暴露使用者需要的能力；应用保持直接，SDK 承担长期兼容承诺。
- 命名描述实际对象与动作；避免含糊的 Manager、Helper 层和难以读懂的布尔参数。
- 所有权清楚；复制、共享引用和锁都有实际理由，不能只为消除编译错误增加复制。
- 可恢复的输入、网络、数据库和插件错误不以 panic 表达；错误保留可行动的类别与原因。
- 不跨外部等待持有共享锁；取消和资源关闭有明确所有者。
- 公共 API 文档说明副作用、失败和取消；测试验证行为、往返和不变量，不照抄实现分支。
- 使用不安全代码须有必要性、局部封装和平台验证；格式、静态检查与依赖约束交给工具。

这些规则是选择与取舍，不能用减少行数、消灭所有抽象或将所有东西泛型化作为质量指标。代码质量的实际结果是：行为可理解、边界可验证、故障可定位、改动不牵动无关模块。

## 2. 核心职责与不变量

核心必须拥有的决策：可信调用身份、资源归属、权限交集、执行和操作编号、资源预算、运行代次、投递事实与审计。领域扩展不能直接修改核心数据库或替换授权结论。

可以由插件实现的能力：模型协议、平台接入、语言运行、外部生态适配、检索和解析、沙箱后端、可选工作流、语音与媒体服务。边界不是“所有逻辑都放插件”，而是“可替换实现通过已定义授权接口工作”。

安装程序、核心和 SDK 之间不重复维护业务规则。新 HTTP API 与旧兼容层共用合法业务操作，而非共用旧内部对象。

## 3. 成熟技术的使用原则

| 领域 | 实现目标 | 应避免 |
| --- | --- | --- |
| Rust 工具链 | 实施时核验稳定版本、明确 MSRV，锁定依赖并可重建 | 使用“latest”漂移配置发布不可追溯包 |
| 开发环境 | mise 统一工具版本与任务入口；uv 管理 Python 项目/环境 | 要求用户手工维护多套解释器路径 |
| 存储 | 维护中的 SQLite/PG 驱动与迁移设施；业务语义统一 | 自制数据库协议或用不同业务逻辑凑双支持 |
| RPC 与传输 | 采用现有 RPC 规范、库和传输设施，补充必要的领域能力与状态契约 | 手写通用解析器、协议栈或把内部对象序列化当 API |
| 身份与秘密 | 成熟加密、密码/Passkey/OIDC 实现，分离密钥与数据 | 自制密码学或把密钥交给模型 |
| 前端 | 成熟的 TypeScript 组件、表单、查询、路由与可访问基础；按需加载 | 为每个页面重造状态、鉴权或表单校验体系 |
| 桌面 | Tauri 与可追溯 sidecar；复用受测后端 | 三套不同业务后端，或仅能开发启动的“安装器” |
| 生态发现 | 标准包元数据、Git 来源与可选目录 | 为安装普通插件强制依赖中心账户 |

具体库由实现时的维护状态、平台支持、许可、依赖体积和真实验证选定。本设计不要求某个前端框架、某个向量库或某个 ORM，避免将内部工具选择误当产品能力。Rust、双数据库、可选 Valkey、Tauri 路线、mise/uv 和四语言 SDK 是已确定约束。

Python 原生插件通过标准入口点发现，加载失败与元数据错误可分别诊断；不能运行任意包顶层代码来“扫描”全环境。[PyPA 入口点规范](https://packaging.python.org/en/latest/specifications/entry-points/)

GitHub topic 使用小写字母、数字和连字符。因此原生发现建议采用 rstrbot-plugin，旧生态兼容采用 astrbot-plugin；清单与搜索别名保留用户要求的 astrbot_plugin 标识。名称与标签不是可信身份，安装仍须校验来源与权限。[GitHub topic 规则](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/classifying-your-repository-with-topics)

## 4. 公共协议必须回答的问题

协议规范至少完整定义：如何握手与协商版本、如何发现能力、如何关联请求、如何拒绝无权操作、如何传递流、如何取消、如何报告错误、如何结束、如何重连以及如何清理。

每个工作进程绑定安装身份、工作区实例和短期运行授权；旧进程的回包只能影响所属代次。核心进程与工作进程可以双向请求，但彼此请求的允许集合不相同。主从对接只是明确控制权和消息归属，不能把“来自子进程”当作可信数据。

同机 Unix socket 与 Windows named pipe 不承担全部鉴权。需要验证服务身份、限制本地权限、绑定实例并防止误连同机另一个部署。远程传输独立提供认证和加密；不能把本机私有通道无验证地公开。

慢消费者有有界缓存或重同步机制。消息大小、附件引用、并发请求数和异常帧都有限制。协议应允许明确的可选能力，未知能力不能被当成默认允许；取消、健康与关闭消息在负载下仍有处理机会。

## 5. SDK 和插件文档交付目录

未来的插件开发文档必须包含以下完整章节，各语言等价。这里定义章节与结果，不提前编写未实现 API 的示例代码。

1. 插件、实例、运行时与工作区是什么，生命周期和权限如何协作。
2. 四种语言各自从新目录到成功运行的完整入门，包括依赖、发现、版本和诊断。
3. 清单、稳定身份、配置类型、国际化、权限申请与来源校验。
4. 事件、命令、钩子、工具、结构化输入、流式输出、取消与后台任务。
5. 模型供应商接入、协议能力、不透明状态、认证与用量归因。
6. 平台适配器、附件、回执、重连、主动消息及独立 MCP 启动。
7. 私有数据与共享数据、持久化接口、配置继承、版本迁移和备份导出。
8. 原生 Python 入口点、旧兼容加载器、OpenCode/Pi 适配与不支持能力的诊断。
9. 沙箱、网络、文件、秘密与运行授权；哪些隔离保证取决于系统。
10. 安装、热重载、停用、卸载、回滚以及进程树回收。
11. 真正可运行的公共示例、协议测试、真实插件测试、故障注入和性能测量。
12. 版本兼容政策、弃用时间、迁移指南、接口与错误码索引、Markdown/机器可读文档入口。

文档不能要求开发者猜测核心类、复制私有函数或依赖未经声明的导入。每个示例对应明确 SDK 版本和验证记录。

## 6. 质量门槛

格式、严格 Clippy、单元/集成测试、公共文档和依赖检查必须在受支持组合执行。语法检查、编译、模拟后端、真实服务、平台原生安装、长稳态运行分别记账；任一层不能代替另一层。

不得通过删测试、吞错误、全局禁用 lint、伪造计数或把未执行项标绿完成验收。平台例外保留原因与独立测试；确有必要的局部 lint 例外需解释而非批量压制。

性能优化先测量可重复场景。报告内存包括核心、工作进程、语言运行时与必要附属服务；分别显示常驻、峰值与缓存。简化优先减少重复状态与重复协议转换，而不是拿掉权限或恢复记录。

## 7. 实现阶段必须保留的证据

需求编号、提交版本、锁文件、平台与依赖、测试输入、实际结果、失败日志、产物校验、CI 运行链接、已知限制构成一份发布记录。复现工具和测试数据在实施阶段提供；当前设计包不含具体实现代码。

对应能力只有在其验收通过后才从“设计完成”改为“实现完成”。对真实第三方服务未验证的样本写明模拟范围；没有供应商费用、平台凭据或原生机器时保留未执行状态，不补造证据。
